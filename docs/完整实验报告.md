## 2. 数据收集与构建（v1）

### 2.1 ShareGPT 原始池的三个问题

官方脚本 `prepare_data.py` 拉下 **120,675** 条 ShareGPT 对话。实测发现：

| 问题 | 数量 | 后果 |
|---|---|---|
| 重复 id | **52,052** 条 | 去重后只剩 68,623 |
| 以 assistant 开头 | **24,611** 条（35.9%） | regeneration 直接报错 `Data starts with an assistant message` |
| 结尾非 assistant | 3 条 | 同上 |

如果按"失败即丢弃"处理，30k 抽样后 train 只剩 18,398，**低于方案自定的 20k 门槛**——这是原方案的一处内部矛盾。我们的处理是在**候选池**里先剔除结构无效对话：68,623 → **44,009**，再按 seed=42 抽样 30,000（28,500 train / 1,500 eval）。

### 2.2 Target regeneration

用 Qwen3-1.7B 自己重写回答（不是用原始 ShareGPT 回答，也不是用更大的模型代生成——EAGLE-3 的训练数据必须是 target-specific 的）：

```
concurrency 32 · max_tokens 512 · temperature 0.8 · top_p 0.95 · top_k 20
```

- 30,000 条全部成功（0 失败），约 3.6 小时，~2.2 条/秒
- 使用固定的 no-thinking Jinja 模板，输出中 `<think>` 出现率 0

### 2.3 过滤

`filter_zero_loss.py`：用与训练完全一致的 tokenizer + 模板，按 `max_length=2048` 截断后检查 loss mask。

- 30,000 → **22,904**（21,750 train / 1,154 eval），保留率 **76.3%**
- 丢掉的 24% 是长对话被截断后只剩 user 部分、没有可训练的 assistant token
- 实测 token 长度：p50 = 1,015，p90 = 2,179，**18.6% 超过 2048**

## 3. 数据扩展（v2）

### 3.1 第二台机器上的 30k：重叠 68.6%

我们在另一台实例上按同一方案又跑了一遍 ShareGPT 管线。两批 30k 逐条比对：

```
ours 30,000 唯一 id
peer 30,000 唯一 id
重叠         20,574  (68.6%)
合并唯一     39,426
```

**同一池子、同一 seed，只是去重策略不同（id vs 内容）→ 高度相关。** 这是"多跑一台机器就能翻倍数据"的直觉的失败。

### 3.2 用第二个语料库补齐

从 UltraChat 取 35,000 条 → 结构过滤 34,995 → 取 30,000 生成。实际生成到 15,001 条（受时间预算控制）→ 过滤后 **13,435**（保留率 89.6%，比 ShareGPT 高，因为对话更短）。

### 3.3 最终数据

| 来源 | 生成 | 可用 |
|---|---|---|
| ShareGPT（含对端合并） | 39,426 | 30,149 |
| UltraChat | 15,001 | 13,435 |
| **合并去重** | 54,427 | **43,584** |
| 95/5 切分（seed 42） | — | **train 41,405 / eval 2,179** |

## 5. 评测方法

固定 benchmark：**90 条 prompt**（30 对话 / 30 数学 / 30 代码），tokenizer 预编码成 input_ids，避免模板差异。

采样口径固定：`temperature=0, top_k=1, top_p=1.0, ignore_eos=True`，baseline 与 EAGLE 完全一致。

- 吞吐：`输出 token 数 / 墙钟时间`，C=1 / C=4 / C=8，120 请求（v1/v2 为 90 请求 × 128 token）
- acceptance：服务端 `spec_accept_length`
- 一致性：10 条 greedy、64 token，逐字比对

## 6. 结果总表

### 6.1 4090-48G + SGLang（v1 / v2，128 token）

| 配置 | C=1 | C=4 | C=8 | acceptance | speedup |
|---|---|---|---|---|---|
| v1 baseline | 230.4 | 781.4 | 1464.0 | — | 1.000x |
| v1 EAGLE | 256.9 | 843.3 | 1478.7 | 2.090 | **1.115x** |
| v2 baseline | 234.0 | 791.1 | 1493.0 | — | 1.000x |
| v2 EAGLE | 283.6 | 954.8 | 1777.4 | 2.268 | **1.212x** |

TPOT：v1 4.22 → 3.80 ms；v2 4.18 → 3.44 ms。

### 6.2 4080S + SGLang：k 扫描与 tree（v2 draft，128 token）

| 配置 | C=1 吞吐 | speedup | acceptance | O |
|---|---|---|---|---|
| baseline | 173.4 | 1.000x | — | — |
| chain k=2 | 200.2 | 1.154x | 1.973 | 1.710 |

**k=3 是 chain 的最优点**；tree 形态把 acceptance 再推到 2.50、加速比 1.32x。

### 6.3 4080S + vLLM：三种 draft 的同台对比（128 / 1024 token）

**我们自训的 draft 在 vLLM 下比腾讯开源权重快 6.7%**（1024 token），acceptance 也略高。

### 6.4 同一份 draft、两个引擎（4080S，128 token）

用**我们自己的 v2 draft**，只换引擎：

| 引擎 | baseline | EAGLE | speedup | acceptance |
|---|---|---|---|---|
| SGLang 0.5.9 | 173.4 | 211.4 | 1.219x | 2.175 |
| **vLLM 0.11.2** | 152.3 | **242.1** | **1.590x** | 2.33 |

> vLLM 的 baseline 更慢（152 vs 173），但 EAGLE 更快 → **加速比差 0.37x**。
> 用 AngelSlim 权重做同样的对照，结论一致（1.149x → 1.534x），说明这不是某个 draft 的偶然。

### 6.5 与 AngelSlim 官方公布数字对比

## 7. 核心分析：加速比到底由什么决定

### 7.1 分解公式

```
speedup S = τ / O
τ = 每轮接受的 token 数（acceptance length）
O = 每轮验证耗时 ÷ 单 token 耗时
O = 1 + k·[(1-r) + δ],  δ = W_draft / W_target,  r = 固定开销占比
```

实测反解 O：

| 配置 | τ | S | O |
|---|---|---|---|
| 4090 / SGLang / v1 k3 | 2.090 | 1.115 | 1.874 |
| 4090 / SGLang / v2 k3 | 2.268 | 1.212 | 1.871 |
| 4080S / SGLang / v2 k3 | 2.175 | 1.219 | 1.785 |
| 4080S / SGLang / tree t2·d8 | 2.500 | 1.324 | 1.889 |
| 4080S / vLLM / **我们 v2** / 128tok | 2.33 | 1.590 | **1.465** |
| 4080S / vLLM / **我们 v2** / 1024tok | 2.33 | 1.879 | **1.240** |
| 4080S / vLLM / AngelSlim / 128tok | 2.27 | 1.534 | 1.48 |
| 4080S / vLLM / AngelSlim / 1024tok | 2.30 | 1.761 | 1.306 |
| H20 / vLLM / AngelSlim / 1024tok（官方） | 2.17 | 1.687 | **1.29** |

**O = 1.24 已经贴着理论下界**：`1 + k·W_draft/W_target = 1 + 2×(274MB/3.4GB) ≈ 1.16`。
也就是说在 vLLM + 1024 token 这个组合下，软件开销几乎榨干了。

### 7.2 三个变量的贡献

| 变量 | 影响 | 证据 |
|---|---|---|
| **推理引擎** | O 1.79 → 1.47（**最大**） | 同一份自训 draft，SGLang vs vLLM |
| **输出长度** | O 1.47 → 1.24 | 128 vs 1024 token，同引擎同 draft |
| **硬件** | O 1.24 → 1.29 附近（最小） | 4080S vs H20（后者用 AngelSlim 权重） |

**"他们比我们快"的部分，2/3 来自引擎，1/3 来自卡；而把引擎和输出长度都用对之后，我们的 O 已经比他们的还低。**

### 7.3 机制：vLLM 把 draft 编译了

vLLM 启动日志：

```
Using cache directory: .../torch_compile_cache/.../eagle_head
Compiling a graph for dynamic shape takes 6.34 s
```

vLLM 对 EAGLE draft head 做 **torch.compile + CUDA graph**；SGLang 0.5.9 的 spec 路径对这个小模型是 eager 执行。

物理量级：
- draft 权重 274 MB ÷ 717 GB/s ≈ **0.38 ms/步**（真实计算）
- 实测每步多出 ~0.5 ms → 纯 Python/kernel-launch 开销
- δ 从理论 0.08 涨到 0.27，O 里多出的 0.5 全是软件

**这也解释了为什么"换更快的卡"没用**：δ 是 draft/target 的权重比，带宽同时作用在两者上，比值不变。带宽只提高绝对吞吐，不改加速比。

### 7.4 为什么 vLLM 的 baseline 反而更慢

vLLM 152.3 vs SGLang 173.4 tok/s。vLLM 的调度器更重、单请求延迟更高，但在投机解码路径上它的编译/图捕获优势足以反超。**这说明"选引擎"不能只看 baseline，要看整条 spec 路径的实现质量。**

## 8. 输出一致性：5/10 的成因

10 条 greedy prompt、64 token，baseline 与 EAGLE 有 5 条不一致，但：

- **EAGLE 自身两次运行 10/10 逐字一致** → 不是采样随机性
- 分歧都发生在第 40–60 个 token 之后，且是语义上合理的分支点
- v1/v2 两轮、两个 draft、SGLang/vLLM 都复现同样的 5/10

**成因**：target 在"批量验证 4 个位置"与"单 token decode"两种前向下，bf16 GEMM 的形状不同，logits 有微小差异；在近似平票处 argmax 翻转后逐步放大。

**结论**：要求"投机解码与 baseline 逐字一致"在 bf16 下基本不可能满足——它假设了比特级等价，而实际只有"精确算术下等价"。要么用 fp32（丧失加速意义），要么把验收标准改成语义等价 + 分布指标。

## 10. 结论

1. **数据管线是对的**：严格去重 + 结构过滤 + target 自生成 + zero-loss 过滤，在我们这套 41.4k 数据上产出的 draft 与腾讯开源的**持平略好**——SGLang 下 acceptance 2.175 vs 2.111，vLLM 下吞吐快 6.7%。
2. **数据翻倍有收益但边际递减**：21.75k → 41.4k，acceptance +0.18，加速 +0.10x。
3. **瓶颈在推理引擎**：同一份自训 draft、同一张卡，vLLM 1.590x vs SGLang 1.219x（+0.37x）；再用 1024 token 输出可到 **1.879x**。
4. **2x 只差一步（未实测）**：现在 O 已降到 1.24，2x 只需 acceptance ≥ 2.48；chain k=2 已经 2.33，tree 在 SGLang 上已经 2.50。**vLLM + tree 是下一个该做的实验。**
5. **"逐字一致"这个验收标准应该放弃**，改为语义等价 + acceptance/吞吐指标。

## 12. 局限

- 只在 90 条固定 prompt 上评测（约 1.2 万 token），未覆盖长上下文与真实业务分布
- tree draft 只在 SGLang 上测过，vLLM 的 tree 路径（`num_speculative_tokens>1` 自动建树）未实测
- vLLM 侧的 1024-token 只跑了 24 请求，样本量小于 128-token 的 120 请求
- AngelSlim 的权重是 fp16，我们转 bf16 后测；原始 fp16 加载在 SGLang 上会因 `tie_word_embeddings` 元数据失败（我们已定位并修复）
