# Qwen3-1.7B + EAGLE-3 报告 v2（41.4k 数据）

> 与 v1 的唯一差别是**训练数据量**：21,750 → **41,405**。
> 超参、config、推理配置、benchmark 流程全部与 v1 完全相同。

---

## 0. 结论

数据翻倍带来了**稳定的正向收益**，但距离 2x 仍很远：

| 指标 | v1（21.75k） | **v2（41.4k）** | 变化 |
|---|---|---|---|
| acceptance (C=1) | 2.090 | **2.268** | +0.178 (+8.5%) |
| 吞吐 C=1 | 230.4 → 256.9（1.115x） | 234.0 → 283.6（**1.212x**） | +0.097x |
| 吞吐 C=4 | 1.079x | **1.207x** | +0.128x |
| 吞吐 C=8 | 1.010x | **1.190x** | +0.180x |
| TPOT | 4.22 → 3.80 ms | 4.18 → 3.44 ms | −0.36 ms |
| 训练末 loss（100 步滚动） | 0.87 | **0.60** | −31% |
| 输出一致性 | 5/10 | 5/10 | 不变 |

## 1. 数据构成

| 来源 | 原始 | 过滤后可用 |
|---|---|---|
| ShareGPT（我们 30k + 对端 30k 合并去重 39,426） | 39,426 | 30,149 |
| UltraChat（Qwen3-1.7B 重新生成） | 15,001 | 13,435 |
| 合并去重 | 54,427 | **43,584** |
| 95/5 切分（seed 42） | — | train **41,405** / eval **2,179** |

两批 ShareGPT 的重叠率 68.6%（同池同 seed 抽样），所以合并后只有 39,426 条唯一对话，不是 6 万。

UltraChat 的保留率 89.6%，高于 ShareGPT 的 76.5%——UltraChat 对话更短，2048 截断损伤更小。

## 3. 为什么还是没到 2x

同一个公式仍然成立：

```
speedup = acceptance / overhead_factor
overhead_factor(v2) = 每轮 7.80ms / 单 token 4.18ms = 1.87
```

- acceptance 2.268 → 1.21x ✓（与实测 1.212x 吻合）
- **2x 需要 acceptance ≥ 3.74**
- 数据翻倍（21.75k → 41.4k）只把 acceptance 从 2.09 推到 2.27（+0.18）

按这个斜率外推，要把 acceptance 再推高 1.47，需要的数据量不是线性增长能解决的——**瓶颈不在数据量，而在"3 步 chain draft + topk=1"这个推理配置的 overhead 结构**。

---

## 4. 一致性仍为 5/10

与 v1 完全一致（同样的 5 条 prompt 不一致、同样的分歧位置特征）。这进一步证明：
**差异来自 bf16 下 batch 验证与单 token decode 的 kernel 路径不同，与 draft 训练量无关。**
