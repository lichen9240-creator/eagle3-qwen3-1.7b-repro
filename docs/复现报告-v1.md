## 3. 为什么是 1.115x 而不是 2x（定量拆解）

### 3.1 每轮验证的真实成本

EAGLE-3 每轮做一次"验证"：draft 连猜 3 步 → 得到 4 个候选 token → target 一次前向验证 4 个位置。

- acceptance = 2.090，即**每轮净产出 2.09 个 token**
- 实测 TPOT = 3.80 ms/token → **每轮耗时 = 2.09 × 3.80 = 7.94 ms**
- baseline 单 token = 4.22 ms → 产出同样 2.09 token 需要 **8.82 ms**

所以：`8.82 / 7.94 = 1.11x`，与实测完全吻合。

**关键比值：每轮开销 ÷ 单 token 开销 = 7.94 / 4.22 = 1.88**

### 3.2 盈亏平衡点与 2x 门槛

这是整份报告的**核心公式**：

```
speedup = acceptance / overhead_factor
```

- overhead_factor = **1.88**（实测，由"4 位置验证 + 3 步 draft"决定）
- 当前 acceptance 2.09 → 1.11x
- **盈亏平衡（1.0x）需要 acceptance ≥ 1.88**
- **2.0x 需要 acceptance ≥ 3.76**

也就是说：在这个推理配置下，acceptance 要从 2.09 提到 **3.76（+80%）** 才可能 2x。这不是"再训一个 epoch"能补的量——按实测边际收益（epoch 0→1 涨 0.13，1→2 涨 0.07），把 acceptance 从 2.09 推到 3.76 至少需要再涨 0.07×20 个 epoch 量级的投入，或者换更高效的配置。

### 3.3 为什么 overhead 是 1.88 这么高

对 1.7B 这种小 target，验证 4 个位置的前向并不比 1 个便宜多少（decode 是 memory-bound，权重读取主导），再叠加 3 步 draft 前向：

- 验证前向（4 位置）≈ 1.2–1.4× 单 token 前向
- draft 3 步 ≈ 0.5–0.7× 单 token 前向（draft 448M 参数，但含 65M 的 32k lm_head，且 3 步串行）
- 合起来 ≈ 1.7–2.1× → 实测 1.88

**方案 §1.2 自己预警过这一点**（"1.7B target 本身很快，draft 固定开销占比高，必须把 acceptance 做上去，否则会退化"）。本实验用数据把这个警告量化了：**对小 target，acceptance 2.0 只能换来 1.1x，1.0x 的盈亏平衡点就在 1.88**。

### 3.4 为什么 acceptance 只有 2.09

| 因素 | 官方 8B 配方 | 本实验 | 影响 |
|---|---|---|---|
| 数据量 | 全量 ~120k | 30,000（过滤后 21,750） | 训练信号少 ~5.5× |
| epochs | 10 | 3 | 训练量少 3.3× |
| max_length | 4096 | 2048 | 长对话被截断，长上下文样本薄 |
| 有效步数 | ~120 万 | 65,250 | 少 ~18× |

训练侧的 acc（teacher-forcing 下一步命中率）最高到 0.61–0.70，但 EAGLE 的 acceptance 是多步联合接受率，会随步数衰减——acc 0.65 对应的 acceptance 2.09 是合理的，不是 bug。

## 4. G10 一致性 5/10 的归因

**事实**：
- 10 条 greedy prompt、64 token，baseline 与 EAGLE 有 5 条不一致
- 分歧点都在**第 40–60 个 token 之后**（前 171–335 字符完全一致），两边都生成满 64 token
- 分歧处是语义上合理的不同分支（如 "the meaning and the relationships" vs "the main idea and specific details"）

**决定性验证**：把同样 10 条在 EAGLE 上**再跑一遍**，结果 **10/10 逐字一致**。

结论：**输出差异不是采样随机性，而是确定性的 kernel 路径差异**——target 在"4 位置批量验证"和"单 token decode"两种前向下，bf16 GEMM 的形状不同，logits 有微小差异；当两个候选 token 概率接近时 argmax 翻转，之后逐步放大。

**这意味着方案 G10 的"10/10 逐字一致"在 bf16 + 投机解码下基本不可能满足**——它假设了比特级等价，而实际只有"精确算术下等价"。这是方案的一处硬伤，不是执行错误。

要真正满足 10/10，只有三条路：fp32 推理（慢 2–3 倍，失去意义）、开启 SGLang 的 deterministic 模式并统一 kernel 路径（需验证是否支持）、或把验收标准改成"语义等价 + 分布指标"（如 KL/acceptance 统计）而不是逐字比对。

## 5. 反思

### 5.1 判断对了的地方

1. **数据规模是上一轮失败的主因**——上一轮 582 条有效样本、acceptance 1.39；这一轮 21,750 条、acceptance 2.09。方向正确。
2. **用 target 自己 regeneration**——避免了分布偏移，训练收敛稳定。
3. **严格不调参**——所有门禁按手册跑，没有为了数字好看偷改超参，所以这份数据是可信的。
4. **提前预演**——G9 导出断言和 sdpa 后端都在正式步骤前验证过，避免了最后一步翻车。

### 5.2 判断不足的地方

1. **没有在开跑前算"盈亏平衡 acceptance"**。如果一开始就算出 "overhead 1.88 → 2x 需要 acceptance 3.76"，就会知道 2x 在这个配置下不可达，可以省下 5.6 小时训练和 ¥16。
2. **对 G10 的可行性没有预判**——方案写的 10/10 在 bf16 下不现实，应该在 G0 阶段就指出。
3. **acceptance 的预期偏乐观**——方案的门槛定在 2.0，而 2.0 刚好只比盈亏平衡点高 0.11，几乎注定只能拿到 1.1x 左右。

### 5.3 一句话总结

> **方案在"能不能复现出 acceptance ≥2.0"这个目标上是成功的（2.090），但在"加速"这个真正的目标上，它选的配置（1.7B target + 3 步 chain draft）把盈亏平衡点推到了 1.88，导致 2.0 的 acceptance 只能换来 1.11x。2x 不是训练不够，是配置的数学上限不够。**

## 6. 如果要真的做到 2x，需要什么

按 `speedup = acceptance / overhead` 这个公式，只有两条路：

### 路线 A：把 acceptance 推到 ≥3.8（保持 overhead 1.88）

| 手段 | 预期 acceptance | 成本 |
|---|---|---|
| 全量 120k 数据 + 10 epochs + max_length 4096（对齐官方 8B 配方） | 3.0–3.8 | 训练 ~40–60 小时，约 ¥120–170（超 ¥100 预算） |
| 在上面基础上加 topk>1 的 tree draft（num_draft_tokens 8–16） | 4.0+ | 推理端每轮验证变贵，overhead 会上升，需重新算平衡点 |
| 领域内数据（数学/代码各训一个 draft） | 该领域 3.5+ | 需多套 draft，部署复杂 |

### 路线 B：把 overhead 压到 ≤1.0

| 手段 | 效果 | 代价 |
|---|---|---|
| draft 减到 2 步（num_steps=2, draft_tokens=3） | overhead ≈1.5 | acceptance 会掉到 ~1.7，speedup ≈1.13，基本不变 |
| draft 词表从 32k 砍到 8k | draft lm_head 从 65M 降到 16M，单步快 ~15% | 需重训，acceptance 可能略降 |
| draft 量化到 fp8/int8 | draft 前向快 ~30% | 精度损失，需验证 |
| 换更小的 target（0.6B） | target 更快，draft 相对更贵 | 方向相反，通常更差 |

**最现实的路径**：路线 A 的"对齐官方配方"——但按当前 ¥2.88/h 的价格，40–60 小时训练约 ¥120–170，**超过方案自己定的 ¥100 硬上限**。
